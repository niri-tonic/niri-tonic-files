# Filen connectors

Filen is available through an optional, separately executed adapter using the
official `@filen/sdk`. Each configured instance has its own name, credentials,
process and authenticated session. The sidebar shows both the name and **Filen**.

## Install

Install Node.js 22+ and npm, in addition to the Rust/GTK
requirements. From this repository:

```sh
make filen                      # Install the locked SDK dependencies locally
make install                    # Install the app and adapter sources
make install-filen              # Install the SDK runtime under the same PREFIX
```

For development, `make filen` followed by `cargo run --release --locked` is enough.
For another installation prefix, pass the same `PREFIX` to both installation
targets. No filesystem mount, FUSE service or automatic synchronization is needed.

The Rust application remains GPL-3.0-only. The separate SDK adapter is
AGPL-3.0-only; its license and dependency details are in `plugins/filen/`.

## Two accounts

Add instances to the existing `connectors` mapping in `config.yaml`:

```yaml
version: 1
connectors:
  local:
    read_only: false
  instances:
    - id: personal
      name: Personal files
      type: filen
      enabled: true
      read_only: false
      auth:
        email: personal@example.com
        password:
          env: FILEN_PERSONAL_PASSWORD
        # Set only when the account requires 2FA:
        # two_factor_code:
        #   env: FILEN_PERSONAL_2FA

    - id: work
      name: Work documents
      type: filen
      enabled: true
      auth:
        email: work@example.com
        password:
          secret_service: filen-work-password
```

IDs must be unique safe slugs, including across reserved connector slots. `local`
is reserved. Duplicate a block with a new ID to add another account. `enabled:
false` hides an instance and prevents it from starting; disabled instances may
omit authentication. `read_only: true` disables mutations but still permits
copying files out of the account. Restart after editing configuration.

Passwords and optional 2FA codes accept `env` or `secret_service` references,
or an explicit `value` string for configuration generated by tools such as chezmoi.
See [credential sources and gopass templates](secrets.md). A bare password scalar
is not accepted; a literal uses `password: {value: "YOUR_PASSWORD"}`.
Environment references must be set in the environment that launches the app.
For example, read a password without putting it in shell history:

```sh
read -rsp 'Filen password: ' FILEN_PERSONAL_PASSWORD
export FILEN_PERSONAL_PASSWORD
niri-tonic-files
```

Secret Service references use `secret-tool` (provided by libsecret tools):

```sh
secret-tool store --label='Filen work account' \
  service niri-tonic-files key filen-work-password
```

This prompts for the value locally. References are resolved lazily on a worker
when connecting. Resolved credentials travel over the adapter's private stdin,
not command arguments, logs or session files. When using `value`, the literal is
stored in the YAML; `env` and `secret_service` keep only their references there.
Adapter environments are
restricted so one account process does not inherit other account password variables.

A valid current 2FA code is needed when establishing a new session. The running
adapter reuses its authenticated session. After expiration, cancellation or a
process failure, a new login may be necessary; supply a fresh code and reconnect.
An authentication failure does not cause repeated automatic login attempts.

For custom installations, an instance may specify an explicit argv:

```yaml
command: [node, /absolute/path/plugins/filen/adapter.mjs]
```

There is no implicit shell or environment interpolation in this command.

## Navigation and operations

Click an account in the sidebar. Paths are displayed as
`filen://personal/Documents` and can be entered in the bottom path field, passed
on the command line, or stored as favorites. These are application locations,
not mounted local directories. Opening a folder follows the normal alternating
pane behavior. Remote listings refresh periodically (15 seconds); completed
operations request an immediate refresh.

Supported operations include listing/metadata, opening files, file/folder
creation, rename, copy, cut/paste/move, permanent deletion, archive/restore and
favorites. Clipboard data retains the instance ID, so the following work:

- Local → Filen, and Filen → local.
- One Filen account → another Filen account.
- Copies and moves within one account.
- Recursive directory transfers and numbered copy collisions (`name-1.ext`).

Transfers run off the GTK thread and report progress with cooperative cancellation.
Cross-connector transfers spool bounded chunks to private temporary files, then
write the destination. A move removes its source only after copying and checking
the source tree again. Failed or cancelled batches retain completed destination
items and report partial outcomes. Cross-connector symbolic links and special
files are rejected; local-to-local operations retain their existing link behavior.
Remote names must be valid UTF-8.

Archive is this application's sibling `.archive` folder, and Restore moves back
to its parent. It is separate from Filen's file-version history. The Delete UI
command remains permanent deletion without confirmation. The provider also
implements Trash as a separate storage capability.

Remote files opened in another application are downloaded to an account-scoped,
owner-only directory under `$XDG_CACHE_HOME/niri-tonic-files/materialized`
(fallback `~/.cache`). The original extension is preserved for associations.
These are local copies: editing them does not automatically upload changes.
Cross-account copies necessarily decrypt locally and re-encrypt for the destination;
they are not server-side account-to-account copies or background synchronization.

## Collision and failure semantics

Local commits still use atomic no-replace syscalls. Filen does not provide the
same atomic exclusive-create primitive. The adapter performs fresh name checks,
uploads to unpredictable staging names, and publishes with non-overwriting rename.
It declares `atomic_move: false`; an unrelated client can still race the provider's
final checks. This must not be treated as a transactional backup/sync engine.

Interrupted remote operations can leave `.niri-transfer-*` staging items or a
partially copied directory. Data is retained rather than deleted during ambiguous
failure recovery. Enable `view.hidden: true` to inspect staging items. Refresh the
affected folders before retrying a mutation. Host and adapter never automatically
replay an ambiguous mutation after disconnect.

## Testing

Tests use an injected SDK and local mock accounts. Live authentication/2FA,
encrypted service transfers, quotas and external-client races remain unverified.
See [testing](https://github.com/niri-tonic/niri-tonic-files/blob/main/docs/validation.md)
for commands and desktop scenarios.
